# Portable request archive v1

Implements item 3 of [#112](https://github.com/Cujuju/spillway/issues/112). The canonical TypeScript record contract is `src/shared/archiveExport.ts`. This is a local, unencrypted, versioned JSON Lines export of the [request archive](request-archive.md), independent of encrypted accounting/history `--data-export` / `--data-import`. Those transfer commands and their key contract are unchanged. Spillway does not import portable archives into Activity requests or live capture tables. The separate [eval case consumer](eval-cases.md) validates bounded files into pinned snapshots in the existing encrypted worker database.

## Selecting and saving

In Activity → Traces, choose **Export** on a branch's card. A session exports every archive entry with its exact session ID in the shown time frame (all matching pages); an unassigned exchange exports its own stable trace identity. Optional `ids` in the API intersects a filter and reports unmatched IDs in `manifest.unresolvedIds`. Dates are inclusive UTC ISO instants after conversion from the UI's local date/time inputs. The saved manifest records the normalized selection and snapshot time. Search uses the archive's existing literal keyword/FTS behavior.

Raw payloads default off. **Include previously recorded raw bodies and WebSocket messages** applies to the next preview. It exports only payloads already recorded under the archive opt-in policy, including saved bodies retained after recording was disabled. Export never turns recording on, reconstructs expired bodies, reads auth/config files, or imports prompts from client logs. Original metadata and optionally bodies may contain private text or user-supplied secrets; files are unencrypted and screen email masking does not redact them. Headers, query strings, provider-hidden content and upstream executor bodies are outside capture/export's boundary.

Preview shows counts by capture state, snapshot bytes, payload policy and exact frozen selection. Save opens a native local file dialog. Progress, cancellation and errors stay in the Export dialog. Changing the raw-payload toggle does not change an existing preview. Prepare a new preview to use it. Closing the dialog cancels an unsaved preview or unfinished write.

## Stream and integrity contract

The file is UTF-8 without a BOM. Every JSON object occupies one physical line ending in exactly LF (`0a`), including the final line. Embedded protocol newlines are JSON string escapes. Order is:

1. One `type: "manifest"` object, `format: "spillway.request-archive"`, `version: 1`.
2. Exactly `manifest.records` objects with `type: "capture"`, sorted newest first by `(entry.at, entry.id)`.
3. Exactly one `type: "complete"` trailer, followed by EOF.

The trailer's `sha256` is lowercase SHA-256 over the **exact emitted UTF-8 bytes of all preceding lines, including their LF terminators**. It excludes the trailer itself. `bytesBeforeTrailer` is that prefix's byte length, not a JavaScript string length. `records` must match both manifest count and actual capture-line count. `payloadStates` counts included/omitted/unavailable/malformed payloads. A missing trailer, count/hash/byte mismatch, unexpected line, trailing record or unsupported format/version makes the file invalid/incomplete. Do not accept or present such a file as a completed export. SHA-256 detects changes; it does not authenticate the producer.

Consumers should read incrementally with a 32 MiB maximum line size, validate the envelope/version and all limits before allocating further, reject duplicate stable IDs, and verify the trailer before committing imported/evaluation data. Persist unknown keys when forwarding v1 records; consumers may ignore them for interpretation. Do not guess a different major version. JSON serialization/whitespace changes require recomputing the trailer. Portable v1 can be consumed independently of Electron, SQLite, Spillway's encryption key and authentication files.

`payload.sha256`, when included, hashes the UTF-8 bytes of `JSON.stringify(payload.data)` as emitted by Spillway (property order is request, response, requestType, responseType, requestEncoding, responseEncoding, format, requestDecoded, responseDecoded, frames). Other languages should preserve original property order and use compact JSON with Unicode characters and standard JSON escaping; the whole-stream trailer is the authoritative integrity check when reserialization differs. Absent payloads have null data/hash. No consumer may turn `omitted` into an empty conversation or treat HTTP 200 as task success. Manifest `taskOutcome` is always `unknown`.

## Manifest

`id` identifies the export job, not a request. `createdAt` and `expiresAt` describe its frozen snapshot. `selection` carries normalized query, optional exact archive IDs and explicit `includeRecordedBodies`. `records`, `snapshotBytes` (encrypted staging content before serialization overhead), `captureStates`, `unresolvedIds`, `recordingPolicy` and `captureDiagnostics` summarize the snapshot. Diagnostics retain epoch, sequence, drops, observed gaps, restarts and rejected records. Drops and gaps may overlap; do not add them or treat these counters as proof of losslessness. `boundary` is `observed-downstream-only`. `attemptLimit: 200` and `attemptCompleteness: "bounded-recorded-links"` state the archive's link boundary.

## Capture and attempt records

`entry` is archive schema v1: stable `id: "trace:<full inbound trace>"`, exact `traceId`, nullable `captureId`, `captureEpoch`, `captureSequence`, time, session/client/provider/requested-model summary, method/path/HTTP status, logical stored bytes, and capture `state`/`reason`. IDs are never SQLite row numbers or short log IDs. Empty model/provider strings and null dimensions retain their existing unknown meaning. One trace can include many upstream attempts; the latest correlated attempt supplies summary dimensions and does not identify a single task outcome.

Capture states remain `unknown`, `missing`, `pending`, `partial`, `complete` or `expired`, independently of payload export state. `complete` means finalized observed downstream exchange/messages within capture limits, not semantic/task/upstream completeness. A pending WS snapshot remains pending; expired data stays expired. If saved payload detail is malformed, metadata still exports with `payload.state: "malformed"`, reason `invalid-stored-detail`, and null data/hash. Invalid saved attempt links produce `attemptsState: "malformed"` and an empty attempts array rather than fabricated links. Valid link arrays have `attemptsState: "recorded"`; this does not assert all original attempts survived.

`attempts` retains each link's `requestId`, nullable `selectionId` and `at`, plus nullable `provenance`. New real proxy observations persist an allowlisted provenance object with source (`proxy`), requested model, effective model, reasoning effort, provider, client, session and parent-session ID, observed downstream/upstream transport and fallback code, failed flag, failure HTTP status, measured latency and TTFT. Unknown values are null, never zero measurements or inferred defaults. No account/auth index, credential, arbitrary error string, user-agent header, tokens or account config is copied into provenance.

These new provenance fields and the three link identifiers outlive Activity request retention and body expiry **with their archive identity**: at most 200 saved links per identity and at most 20,000 archive identities total. Oldest identity eviction or archive/Activity deletion removes them. Earlier links written before this feature have no persisted provenance and export `provenance: null`; the exporter does not infer it or reread client logs. This feature does not backfill pruned Activity metadata. Provenance strings are bounded to 512 characters and retain unknown values. Stable request/selection IDs are preserved exactly within the per-record 2 MiB link budget. Attempt-link order is the archive's stable internal identity order; use `at` for chronological views.

## Protocol, tools and messages

`payload.representation` is always `downstream-protocol-v1`. `state` is:

- `omitted`: the export opt-in is off, irrespective of capture state.
- `unavailable`: selected raw export has no retained body/frame content. The archive reason/state is preserved.
- `included`: retained, structurally valid detail is present. The capture may still be partial or pending.
- `malformed`: stored detail cannot be safely represented; no raw fallback is silently called complete.

Included `data` contains request/response text, original content-type/encoding labels, per-direction decoded flags, format (`http`/`websocket`) and frames. Only these known fields are copied. Bodies are observed downstream content; decoded flags, original encoding and capture state must be read together. Unsupported/corrupt encodings may have a bounded base64 fallback produced by capture; export does not decode or relabel it.

HTTP `request`/`response` strings preserve original JSON/SSE protocol text. Claude `messages[].content[]` `tool_use`/`tool_result`, OpenAI/Codex function-call items, tool definitions, call IDs, argument strings and streamed partial JSON stay in their original provider protocol. For example, Claude SSE `data: {"delta":{"partial_json":"..."}}` remains an SSE string, not a normalized assistant message. SSE sentinels, malformed/truncated JSON prefixes and original ordering are retained. Consumers must use content type and state to choose parsing; do not concatenate arbitrary tool JSON into user prompts.

WebSocket frames retain index/direction/time, text/binary type, original payload string and truncation flag. Codex `response.create`, `function_call`, `function_call_output` and response deltas remain application-message JSON inside frame payloads. Binary payloads use capture's base64 representation. Request/response transcripts may duplicate frame information; prefer frames when reconstructing WS ordering and never count both as separate exchanges. WS control frames and provider-hidden reasoning are absent. No normalized messages/training rows are asserted; an eval/replay consumer must interpret protocol variants and explicitly handle omissions, partial payloads, absent terminal model events and unavailable tools.

## Snapshot ownership, bounds and failure handling

Only the Activity worker opens its own keyed database. `archiveExportPrepare(options)` freezes selected metadata, detail revisions and attempt links in one synchronous database transaction in `portable_export_snapshot`, inside encrypted `activity.db`. It uses metadata pages of 50 and stores no plaintext capture spool. Captures arriving after preparation, ordinary pruning and body revisions cannot change the frozen export. User archive/Activity deletion explicitly cancels outstanding snapshots. `archiveExportStatus(id)` returns a body-free job/manifest; renderer `archiveExportSave(id)` opens the native dialog, then invokes worker-only `archiveExportStart(id, absolutePath)`. `archiveExportCancel(id)` abandons a preview or requests streaming cancellation. These are renderer IPC APIs defined in `src/shared/ipc.ts`; the existing accounting-transfer API is independent.

There is one job/snapshot per worker, up to 20,000 records and `min(128 MiB, archive policy body budget + 16 MiB metadata allowance)` staging bytes. Requests exceeding a limit fail atomically and ask for a narrower range or metadata-only export. No record/encoded line may exceed 32 MiB; attempts are bounded to 200 and 2 MiB raw link metadata per record. This bounds staging independently of the archive's live retention budget; it can temporarily add that much encrypted storage. Larger histories need separate date-range files. Preview preparation may briefly occupy the worker while taking the transaction; streaming yields on 64 KiB output writes and reads one frozen record at a time. The entire history is never loaded into memory.

Preview and writing expire after 15 minutes from preparation. Replacing a preview, cancel, expiry, completion/failure and orderly worker close delete the staging rows. Startup initializes the exporter before capture sync, deletes stale rows and removes tracked incomplete output files from prior crashes. Locked/invalid recovery markers are handled independently: they remain recorded, appear in `archiveStatus().exportWarning`, and never stop Activity/accounting startup. New exports retry cleanup and remain blocked while unresolved markers exist, bounding incomplete-file accumulation. Output is written with exclusive creation and restrictive mode (0600 where supported) to a random `.spillway-export-<job UUID>.partial` sibling, flushed/closed, then atomically renamed to the chosen destination. The existing destination survives errors or cancellation before rename. Finalizing the rename is the commit point and is no longer cancelable. A job reports complete/path only after rename succeeds. Disk/open/write/rename failures remain failed, and partial-file cleanup failures report the exact path for manual removal and keep its encrypted recovery marker for the next startup. Cleanup failures use `job.warning`; a successful rename remains complete even if subsequent database cleanup fails. Failed snapshot cleanup is reported and retried on disposal/next preparation/restart. Free encrypted database pages may remain on disk for reuse, as with archive pruning.
